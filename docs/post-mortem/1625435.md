# AB#1625435 — Regression: Page Behind an Open Non-Modal Drawer Still Scrolled

**Scope:** 6 files changed — `package.json` and `package-lock.json` (`auro-library` `^5.13.3` → `^5.14.3`), `test/auro-drawer.test.js` (4 new tests, each run in both viewports), `src/auro-drawer.js` and `src/auro-floater.js` (comments only), `docs/post-mortem/1625435.md`. **No behavioral `src/` change** — the fix is in `auro-library` (AB#1647843); both `src/` edits replace now-misleading comments (see Section 3). No visual or API change.

## Executive Summary

A default, dismissible `auro-drawer` left the page behind it scrollable at desktop widths, while a `modal` drawer locked it correctly. `auro-drawer` has owned no scroll-lock code since `be314cb` ("perf: move scroll lock logic into floatingUI"); the defect was entirely in the shared library, which engaged the lock only when the positioning strategy resolved to `"fullscreen"`. A dismissible drawer above its `fullscreenBreakpoint` resolves to `"dialog"`. One library fix resolved this and the identical `auro-dialog` bug (AB#1625424). The work in this repo is the dependency bump and the missing regression tests.

---

### Section 1 — The Problem

With a standard drawer open and page content tall enough to scroll, the page behind it could still be scrolled by wheel, trackpad, touch, and the arrow and space keys. The blocking (`modal`) presentation already prevented this, so the two presentations of the same component behaved differently.

It reproduced only above the drawer's `fullscreenBreakpoint` (default `sm`). Below it, the strategy flips to `"fullscreen"`, which did lock — so the gap was invisible on narrow viewports.

---

### Section 2 — Root Cause

Not in this repo. `auro-library` `scripts/runtime/floatingUI.mjs` gated the lock on the positioning strategy:

```js
if (element.isPopoverVisible) {
  this.lockScroll(value === "fullscreen");
}
```

and `getPositioningStrategy()` handles `dialog` and `drawer` behavior in one shared branch, returning `"fullscreen"` only when the element is `modal` or the viewport is below the breakpoint — otherwise `"dialog"`.

Because that gate sits in `configureBibStrategy()`, which Floating UI's `autoUpdate` re-runs on every resize and scroll tick, the lock was not merely skipped but actively released for the whole time the drawer was open. That is why no fix was possible in this repo: any drawer-side lock would have been undone within a frame.

Full analysis, including the secondary teardown leak also fixed: `auro-library/docs/post-mortem/1647843.md`.

Worth recording for context: the decision in `be314cb` to centralize this logic was correct and is not being reversed. `docs/post-mortem/1491977.md` §6 explains why the lock is delicate enough to want exactly one implementation — it has to defeat the VoiceOver three-finger swipe, which `overflow: hidden` alone does not, and track the iOS virtual keyboard through `visualViewport`. What went wrong was that the guarantee moved to the library without a test following it in either direction.

---

### Section 3 — The Fix

`auro-library` (AB#1647843, released in 5.14.3) locks for the whole overlay branch (`lockScroll(true)`), leaving the nested `"cover"` strategy scrollable by design, and releases the lock in `disconnect()`. This repo bumps the dependency; no `src/` behavior changes.

One consequence to be aware of: the library's `lockScroll()` sets `aria-modal="true"` on the inner `<dialog>` as part of locking, so dismissible drawers now carry it. **This was reviewed and kept as part of AB#1647843** (see `auro-library/docs/post-mortem/1647843.md`, "Why This Works"). `auro-drawer-content.js` installs a `FocusTrap` whenever the drawer is visible, with no `modal` condition, so keyboard focus cannot reach the background of a dismissible drawer either; a pointer press outside the panel dismisses the drawer rather than reaching the page. `aria-modal="true"` therefore describes what the drawer actually does. Removing it while keeping the focus trap would be the worse combination: a screen-reader user in browse mode could reach background content and hear it read out, but not operate it.

The honest caveat is that only the `modal && !nested` path calls `showModal()`, so on the `showPopover()` path the platform does not make the background inert — containment comes from the component's own `FocusTrap` and dismiss handling, not from the browser. The attribute is also set from inside `lockScroll()`, which couples a scroll concern to a modality assertion; `auro-dialog` (AB#1625424) carries the same coupling. No ticket has been filed to revisit this. Sourcery re-raised it on this PR; if design-system accessibility wants to reopen the decision, that should be a new ticket rather than a change here.

The `src/` edits are all comment-only. `auro-drawer.js` `configureA11y()` carried a comment claiming `role="dialog"` **and** `aria-modal` are both provided natively by `<dialog>`; only the former is, since native modal semantics come from *how* the dialog is opened. `auro-floater.js` `show()` described the `!modal && !nested` path as allowing "free keyboard flow to background content (WCAG 2.1.2)", which `FocusTrap` — installed regardless of how the dialog was opened — has not been true of for some time. A later review pass caught that the corrected comments then over-claimed in the other direction: they said `dialog.open` is never set on the non-modal path, but browsers without the Popover API fall back to `dialog.show()`, which does set it. The comments in `show()`, both `hide()` branches, and `configureA11y()` now name that fallback. `hide()` itself was already correct — it branches on `dialog.open`, so a fallback-opened drawer closes through the first branch. No code changed.

### Section 4 — Test Coverage

The `describe("modal vs non-modal")` block already covered the modal lock, release on close, the nested no-lock case, and restoration of pre-existing `body` inline styles. It had **no non-modal case** — the one presentation that was broken. That is the gap AB#1625435 fell through.

**Tests added** (the suite runs twice, at 900×800 and 300×800, so these are 8 of the 116):

- `should lock page scroll for non-modal drawers (AB#1625435)` — the direct regression test. Asserts `_scrollLocked` and every inline style the lock writes while open, and their release on close.
- `should hold the page still while repositioning a non-modal drawer (AB#1647843)` — re-enters `configureBibStrategy()` for both overlay strategies, the way Floating UI's `autoUpdate` does on each resize and scroll tick, and asserts the lock survives **after each call**. The first version asserted once, after both calls, which could not catch the regression it was named for: the old gate released the lock on `"dialog"` and re-took it on `"fullscreen"`, so the trailing assertion read a locked page either way. Verified by restoring the old gate in `node_modules`: in the mobile pass, where the drawer opens locked and the loop is actually reached, the single-assertion version passed and the per-call version fails with `repositioning as "dialog" must not release the scroll lock`.
- `should restore the scroll offset the page was at` — scrolls a tall page before opening, then asserts the page cannot be scrolled while the drawer is open and returns to the reader's offset on close.
- `should release the page scroll lock when disconnected while open` — covers the secondary teardown leak fixed alongside the main bug, where unmounting an open drawer stranded `body{position:fixed}` with no remaining path to undo it.

Two shared helpers back these: `snapshotPageScrollStyles()`, which starts each test from a known page and restores it afterwards (several existing tests leave a drawer open, and therefore the page locked), and `expectPageScrollLocked()`, which asserts every property the lock sets rather than a single representative one.

Each of the four runs its body in a `try` with the restore in a `finally`. Without that, the one case that matters most — an assertion failing because the regression has returned — is also the case where cleanup is skipped, stranding `body{position:fixed}` and a locked `html` across every following test and the whole second viewport pass. The scroll-offset test also restores `body.style.height` there, since `height` is not one of the properties `snapshotPageScrollStyles()` tracks.

**Revert-proofing.** With the library fix reverted in `node_modules`, the AB#1625435 test fails in the desktop pass and passes in the mobile pass — precisely matching the reported reproduction. With the fix applied, all 116 tests pass.

### Section 5 — Risk Assessment

| Risk | Mitigation |
|---|---|
| Nested drawers wrongly locking | `"cover"` strategy takes a different branch; the existing nested no-lock test now genuinely exercises it against the changed library |
| `modal` or mobile behavior regressing | Both remain covered, and the whole suite runs at both viewports |
| Host application's own `body` styles being wiped | The library saves and restores prior inline values; covered by the existing pre-existing-styles test |
| Placement variants (`left`/`right`/`top`/`bottom`) behaving differently | Placement is purely visual and does not affect which strategy is chosen |
| Jumping two minor versions of `auro-library` (5.13.3 → 5.14.3) | Full suite run against the packed 5.14.x build before the bump; 108 pre-existing tests passed unchanged. Re-run against the published 5.14.3 from the npm registry: all 116 pass |
| **Known, not fixed:** two drawers open at once | Each `AuroFloatingUI` instance saves and restores page styles on its own, so closing two locked drawers out of order can unlock the page early or leave it frozen. Pre-existing in the library; this change widens exposure by making dismissible desktop drawers lock too. Tracked as **AB#1648833** |
| **Known, not fixed:** an open drawer that is moved or remounted | `disconnectedCallback()` calls `hide("disconnect")`, so an open drawer **closes** on any DOM move — even a same-task reparent — and on a remount. Verified in a browser: in both modal and non-modal presentations it comes back closed with the page lock released, so the page is never left frozen. Read from the code but not yet verified at runtime: `hide("disconnect")` also calls `floater.disconnect()`, which removes the trigger listeners, and there is no `connectedCallback()` to re-run `configure()`, so a reconnected drawer likely no longer opens from its trigger. Pre-existing, and outside this ticket's scope. The move case is tracked as **AB#1648808**, whose desired behavior keeps a genuine removal closing as it does today — so the trigger rewiring after a reconnect is not covered by it. Note for whoever picks it up: AB#1648808 says `auro-dialog` "already survives being moved", but a dialog that is moved keeps `open` while dropping out of the top layer (`:popover-open` / `:modal` both go false), so copying the dialog's approach as-is would carry that gap over. `auro-dialog`'s own move/remount gap is not covered by AB#1648808 |

### Key Lessons

1. **Centralizing a behavior does not transfer responsibility for asserting it.** This repo deleted a working scroll lock in favor of the library and deleted its coverage with it. The library gained none. For a while, no repo asserted the guarantee — so it broke silently and stayed broken.

2. **Cover every presentation, not just the interesting one.** The `modal vs non-modal` block tested the modal side of four behaviors and the non-modal side of one. The untested combination is where the bug lived.

3. **Viewport-dual suites need the failing case to be in the failing viewport.** This bug only reproduces above the breakpoint. A test written only for mobile — or a manual check performed only on a phone-sized window — would have confirmed the behavior worked while it was broken for most users.

4. **When the bug is "released, then re-taken", assert between the steps.** The reposition test drove two strategy calls and checked the lock once at the end. The defect released the lock on one call and re-took it on the next, so the end state looked healthy and the test passed against the exact regression it was written for. A test of a state that can flicker has to observe it at every step where the flicker could happen — and the only way to know it does is to restore the bug and watch the test fail.
