# AB#1683370

## Executive Summary

The drawer's documentation says its panel color and text color can be changed by setting two color settings on the drawer. Setting them did nothing: the panel stayed white and the text kept its default color. The drawer now uses the colors a consumer sets, and looks exactly the same as before when nothing is set. Ticket: [AB#1683370](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1683370)

## The Problem

Teams who wanted the drawer to match their own theme, such as a dark background, followed the documented color settings and saw no change. The documentation promised a way to restyle the drawer that didn't work, and nothing else let them restyle it.

## Root Cause

`<auro-drawer>` appends an internal `<auro-drawer-content>` element that renders the panel (`.wrapper`) and styles slotted text (`::slotted(*)`) in its shadow DOM. `src/styles/drawerContentTokens.scss` declared the two public tokens on that element's `:host`:

```css
:host {
  --ds-auro-drawer-container-color: var(--ds-basic-color-surface-default, #ffffff);
  --ds-auro-drawer-text-color: var(--ds-basic-color-texticon-default, #2a2a2a);
}
```

A custom property set on an element wins over the value it would inherit from its parent. A token set on `<auro-drawer>` (or an ancestor, or `:root`) therefore never reached `drawerContentColor.scss`, which read the content element's own default. A regression test run against the unmodified styles failed in both viewports with `expected 'rgb(255, 255, 255)' to equal 'rgb(1, 2, 3)'`.

## The Fix

- `src/styles/drawerContentTokens.scss`: the content element's `:host` no longer declares the public tokens. It declares private defaults, `--_container-color-default` and `--_text-color-default`, each set to the design-token value.
- `src/styles/drawerContentColor.scss`: `.wrapper` and `::slotted(*)` read the public token at the element that uses it, falling back to the private default: `var(--ds-auro-drawer-container-color, var(--_container-color-default))`.
- `test/auro-drawer.test.js`: one test sets both tokens inline on `<auro-drawer>` and asserts the computed panel background and header text color. A second sets the text token on `::part(drawer-wrapper)`, the way `apiExamples/close-button-appearance.html` does, and asserts the header text color.

## Why This Works

Nothing on the content element declares the public tokens any more, so values set on `<auro-drawer>` inherit through to it. The panel and slotted text read the public token where they use it, so a value set on the drawer, on an ancestor, or on the `drawer-wrapper` part all reach them. When no token is set, the fallback is the original design-token default, so the unset case is unchanged. The private default names aren't part of the public API. The `@cssprop` documentation on `<auro-drawer>` already described this behavior and needed no change.

## Outcome

Colors set on the drawer now appear on its panel and text, as the documentation says, whether they are set on the drawer or on the `drawer-wrapper` part. With no colors set, the drawer looks the same as before. The drawer test file passes (132 tests, including the two new ones in both viewports).

## Ticket Completeness

3 of 4 acceptance criteria resolved; 1 partially resolved.

**Resolved**
- Setting `--ds-auro-drawer-container-color` on `<auro-drawer>` changes the panel background: the fallback change in `drawerContentColor.scss` plus the new test asserting `rgb(1, 2, 3)`.
- Setting `--ds-auro-drawer-text-color` on `<auro-drawer>` changes the slotted text color: the same change, with the test asserting `rgb(4, 5, 6)` on the header text.
- New WTR tests covering both tokens set on `<auro-drawer>` are added and pass: two new tests, run in both viewports, in the passing 132-test suite.

**Not Resolved / Partial**
- With neither token set, the drawer's colors are unchanged from today: the fallback chain keeps the original design-token defaults and the existing tests still pass, but no test asserts the default colors directly, so this rests on the unchanged fallbacks rather than a dedicated check.

## Learnings

- A custom property declared on a child's `:host` shadows the value inherited from its parent. Don't declare a public token with a default on an internal child; put the default in the `var()` fallback where the token is consumed.
- Read a public token where it's used, not once at the host. A private property computed at the host from the public token can't see a value a consumer sets lower in the tree, such as on a `::part()`.
- Check API examples against style changes. `apiExamples/close-button-appearance.html` sets the token on `::part(drawer-wrapper)`, and a doc review caught that the first fix broke it.
- Test a documented token the way a consumer uses it: set it on the outer element and assert the computed style inside the shadow DOM. A test on the internal element would have passed against the broken code.
- Run a new regression test against the unfixed code first. Seeing it fail with the expected `rgb(255, 255, 255)` confirmed the diagnosis.
- Documented `@cssprop` entries aren't verified by tooling, so a documented token can silently stop working. A test per documented token catches that.

## Iterations That Didn't Work

The first fix declared private `--_container-color` and `--_text-color` on the content host, each reading the public token with a fallback, and had `.wrapper` and `::slotted(*)` read those. It worked for a token set on `<auro-drawer>` but broke a token set on `::part(drawer-wrapper)`: the private property is computed once at the host, so a value set lower in the tree is never read. `apiExamples/close-button-appearance.html` does exactly that, and its text would have stayed dark on the black panel. A doc review found it after the commit; the fix above reads the public token at the element that uses it.
